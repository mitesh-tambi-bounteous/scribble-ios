Planning-prompt checklist

  • Goal + context — state the outcome; link the ticket/issue if there is one
  • Worktree — ask Claude to work in one; you just see a branch
  • Agent teams — task list + dependencies, dispatched in parallel
  • Right-size models — cheaper/faster models for validation-only agents
  • "Be brief" — keep output concise when you don't need the narration

What makes a good prompt

  • Output contract first — say what "done" looks like
  • Structure it — goal / context+files / constraints
  • Examples — show the format (few-shot); show reasoning for tricky logic
  • Make it verifiable — explicit success criteria
  • Measure, then compress — check the result; keep context tight

Tips from the field

  • Prompt the goal, not the implementation — keep it short; let Claude find the files
  • Read what Claude says — not just the diff; if tone/format is off, say so ("be brief")
  • Roast the plan — ask Claude to grill its own plan, then respond section-by-section
  • Give a reference codebase — clone a relevant repo, point Claude at the path
  • Use screenshots — paste an image of the error/log/UI instead of describing it
  • Let the agent verify its own work — tests / CLI / computer-use; loop a review tool until clean

MobileApp · Plan mode

Walkthrough · built-in plan mode

Ship a change with plan mode

Plan mode is the entry path for well-scoped work: you already know roughly what needs to change. Claude explores read-only until you approve a plan, then executes it. Use this path when the shape of the change is clear; use brainstorming instead when it isn't.

plan mode → review → approve → implement → review diff → commit
repo shipped in this repo's .claude/ plugin auto-enabled via settings.json built-in native Claude Code

Enter plan mode

Press Shift+Tab to cycle the mode indicator to plan mode, or just describe the task and let Claude propose a plan on its own. In plan mode Claude can read and explore the codebase but cannot edit files or run state-changing commands until you approve.

Shift+Tab → plan mode built-in

Describe the task, and ask for a worktree if the repo uses them

State the goal and any constraints in the plan-mode prompt. MobileApp uses the standard worktree convention: git worktree add ~/src/MobileApp-wt/<slug>/ -b <slug>. If MobileApp uses git worktrees to isolate work from the primary checkout, tell Claude to work in one — it creates the worktree as its first action once the plan is approved, so you just see a new branch appear. If the repo doesn't use worktrees, this step doesn't apply and Claude edits in place.

What to put in your prompt

  • Goal + ticket — state the outcome; reference your tracked work item if you use one
  • Worktree — tell Claude to work in one; it creates one, you just see a branch
  • Agent teams — ask for a task list with dependencies + dispatched agent teams so independent tasks run in parallel
  • Right-size models — set each agent's model to its job; use Haiku for validation/check agents (faster, cheaper, more parallel headroom)
  • "Be brief" — add the words "be brief" to keep output concise

Review the plan before you approve it

Read what Claude proposes before exiting plan mode. /code-review plugin is available in this repo (from the enabled code-review plugin) — point it at the plan before approving. A good plan names the specific files/modules that will change, calls out the sequencing and dependencies between edits, and states how the result will be verified (tests, manual check, a specific command). A plan that just restates the request back to you isn't a plan yet — ask for more specificity before moving on.

Approve the plan → Claude starts editing

Approving exits plan mode. Claude leaves read-only mode and begins making the changes it described. Watch the diff as it goes; interrupt if it drifts off the approved scope.

ExitPlanMode built-in

Review the diff before committing

Once edits are done, review the working-tree diff for anything that doesn't trace back to the approved plan — drive-by cleanup, scope creep into unrelated files, or missed pieces. A manual read of git diff before staging is enough for smaller changes.

Commit with a clear message

Write a commit message that explains why the change was made, not just what changed — the diff already shows what. Keep one conceptual change per commit where practical. The safety hooks configured under .claude/, if any, run automatically on the commit — you don't have to invoke them, just don't bypass them.

git commit -m "..." built-in
Pitfall: approving a vague plan just to get to the "fun part" of watching code get written. If you can't point to the specific files that will change, the plan isn't ready — push back before you approve, and don't skip the diff review before committing just because the plan looked solid.
Insight: plan mode assumes you already know roughly what needs to change and just want the approach checked before it happens. When the task is a goal rather than a spec, or there are real design tradeoffs to weigh first, start with brainstorming instead — it's meant to converge on a plan, which you then run through this same review and execute path.

Ship the same change with brainstorming

Brainstorming is the entry path for open-ended or underspecified work: the requirements aren't fully known yet, or there are real design tradeoffs worth talking through before any code gets written. The execution skill enforces TaskCreate-first orchestration: break the plan into tasks with real dependencies, dispatch independent tasks in one message with multiple agent calls, and keep the main agent as orchestrator while builder agents do the editing.

Run the validators and read the output before claiming done. "Should pass" is not "passed" — capture the actual test run, lint output, and diff stat.

A single command handles a "what and why" commit, pushes the branch, and opens a PR with a summary and test plan.

Insight: reach for brainstorming when the request is a goal rather than a spec, when there are multiple viable approaches worth weighing, or when the work touches feature surface that's unfamiliar in MobileApp. When you already know roughly what needs to change, skip straight to plan mode instead — brainstorming's whole job is to get you to that starting point.

Mental model

The 5-Layer Agent Development Kit

Claude Code isn't just AI in your terminal — it's a layered runtime. Each layer solves a problem prompting alone can't. The model is fixed; the harness is the durable lever. Adopt load-bearing layers first, and add the next one only once the previous one is actually working.

One line each · adoption order top→down

The five layers

What each layer is

1 · Memory
CLAUDE.md — durable rules, loaded every session
2 · Knowledge
Skills — procedural expertise, loaded on demand
3 · Guardrails
Hooks — deterministic, runtime-enforced, not advisory
4 · Delegation
Subagents — isolated specialists, own context window
5 · Distribution
Plugins — package once, the team inherits

Most agent failures = a missing layer

  • Forgets conventions? → Memory missing.
  • Repeats setup every time? → Knowledge missing.
  • Inconsistent on risky actions? → Guardrails missing.
  • Context is a swamp? → Delegation missing.
  • Everyone reinvents the wheel? → Distribution missing.
Layer 1 · Memory

CLAUDE.md — durable rules

Loaded at the start of every session. Claude walks up the directory tree and concatenates every CLAUDE.md it finds; imports via @path/to/file chain up to 5 hops. Goes here: architecture rules, conventions, repo map, invariants. Not here: step-by-step procedures (those are Skills).

When to add it: first, before anything else — it's the one file every session reads whether or not the task needs it.

FileLength / structureNotes
.claude/CLAUDE.mdSingle, short fileThe only CLAUDE.md in this repo — harness index
Pitfall: longer ≠ better. Past ~200 lines, adherence drops fast. Lift long sections into @imported sub-files or move procedures into Skills instead of growing the root file indefinitely.
Layer 2 · Knowledge

Skills — procedural knowledge on demand

Reusable playbooks loaded only when relevant — triggered by a slash command or auto-invoked when Claude matches the skill's description to the task at hand. Live in .claude/skills/<name>/SKILL.md.

When to add it: the moment you've pasted the same playbook into a prompt twice. If a teammate asks "how do we do X here" and the answer is more than a sentence, that's a Skill.

SkillWhat it doesNotes
app-store-complianceChecks changes against App Store / Play Store submission rules
async-ai-pipelineGuides work on the SQS-based async AI pipeline
channel-isolation-testingTests the channel-isolation invariantlaunch-blocking
claude-provider-adapterGuides changes to the Claude provider adapter
skia-native-moduleGuides work on the @shopify/react-native-skia native module
submit-to-unlock-invariantTests the submit-to-unlock invariantlaunch-blocking
Pitfall: vague descriptions never auto-fire. Write the description like a search query — include the actual phrases people will type, not a generic summary of the skill's purpose.
Layer 3 · Guardrails

Hooks — deterministic guardrails

Shell commands wired to lifecycle events (PreToolUse, PostToolUse, SessionStart, Stop, SubagentStop). The runtime decides if they run, not the model. Hooks read JSON on stdin describing the proposed tool call; exit code 2 with a "reason" field blocks the action and tells Claude why, so it can course-correct instead of failing silently.

When to add it: when "please don't do X" in CLAUDE.md isn't enough and X must be impossible — secrets in commits, force-push to main, writes to .env files, malformed branch names. Advisory instructions get forgotten under pressure; a hook cannot be talked out of firing.

HookFires onWhat it does
worktree-guardPreToolUse · BashBlocks edits outside a worktree.
secrets-scanPreToolUse · Edit|Write|BashBlocks writes/commands that would leak secrets.

Pitfall: hooks fail silently if the command isn't resolvable on PATH from wherever the hook actually runs. Test the hook standalone (pipe it a sample JSON payload, check the exit code) before trusting it in production, then run /doctor to confirm the harness sees it.
Layer 4 · Delegation

Subagents — isolated specialists

Workers the main agent dispatches to. Each runs in its own context window, own tool permissions, optionally a cheaper or faster model. The main agent gets a summary back, not the noise. Built-ins include Explore, Plan, and general-purpose; a repo can also define its own in .claude/agents/. Subagents can't spawn subagents — no infinite nesting.

When to add it: when a side task is more than roughly five tool calls, or produces logs and exploratory output you don't want cluttering the main thread. Fan out independent subtasks in parallel; keep the main agent as orchestrator, not implementer, once the work crosses that threshold.

Pitfall: don't dispatch a subagent for one trivial action — the context-switch and summarization cost beats whatever context it would have saved.
Layer 5 · Distribution

Plugins — package once, team inherits

Versioned bundles of skills + subagents + hooks + commands. One person enables a plugin, the whole team gets the same behavior — no copy-pasting a .claude/ directory between repos and letting the copies drift apart.

When to add it: when more than one person needs the same skill/hook set and you want versioned, reviewable distribution instead of tribal-knowledge copy-paste. A plugin is also the right home for anything you want to reuse across multiple repos, not just this one.

The safety net

Plan mode

Plan mode is read-only: Claude reads, searches, and explores but cannot edit, write, or run state-changing commands until you approve the plan. Toggle with Shift+Tab. Use it for any non-trivial change — new features, refactors, anything touching more than one file.

Why it matters: plan mode turns "did Claude understand the task?" into a checkpoint you can inspect before any file changes, instead of discovering a misread requirement three edits in.

Under the hood

The worktree pattern

git worktree add checks out a branch into its own directory, sibling to the main checkout, with its own working tree but sharing the same .git history. That gives every task an isolated workspace: no stashing, no branch-switching churn, no risk of two sessions colliding on the same files.

Typical patternterminal
# Claude runs this when you ask in your prompt — you don't type it yourself
git worktree add ../REPO-wt/<slug>/ -b <slug>
cd ../REPO-wt/<slug>/

# Verify before any edit
git worktree list

# Cleanup when the task is done or abandoned
git worktree remove ../REPO-wt/<slug>/
One session per worktree. Never edit main (or your primary branch) directly in the main checkout for real work — stray edits there are the most common way a session's changes get lost or tangled with another session's.

This repo uses the standard convention: git worktree add ~/src/MobileApp-wt/<slug>/ -b <slug>.
