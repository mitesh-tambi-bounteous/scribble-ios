Scribl · Proof of Concept · Decision-grade

Build the POC in Expo (OSS) — one codebase, AWS-hosted.

Recommendation: build the 1-week clickable POC directly in the Expo open-source framework as a single React Native codebase, ship an Expo Web export as the shareable artifact, and validate the native-only risks (finger-on-glass drawing, push) on-device. No throwaway HTML prototype. No Expo-cloud lock-in — build, host, and CI/CD in AWS.

TL;DR & recommendation

Recommendation

Expo-OSS-direct, single codebase. Build the POC in the Expo open-source framework (React Native); use the Expo Web export as the shareable "clickable" link and device dev-builds for the native-only risks. Do not build an HTML prototype first — it would be thrown away and, worse, would dodge the two riskiest things to validate. Use Expo's MIT toolkit only; host and run CI/CD ourselves in AWS.

Three forces drive this:

  • The hard parts are native-only. Scribl's core is a "drawing canvas on your phone — finger-on-glass," and the retention thesis runs on a push-notification habit loop. Mobile web can't faithfully validate touch-draw latency, and web push (especially iOS) can't test a daily-habit loop. An HTML-first prototype validates the easy parts and gives false confidence on the hard ones.
  • HTML-first is a guaranteed rewrite. Web React is not React Native — components, navigation, and the canvas would all be rebuilt. Production is RN/Expo and the team is RN-oriented, so a web prototype is pure throwaway.
  • One Expo codebase gives us both audiences. react-native-skia renders on web via CanvasKit (WASM) and Expo targets web from the same codebase — so a single build yields a shareable Expo Web link (desirability) and device builds (feel + push). No rewrite; the POC seeds the real app.

Scope answers locked with Rob: POC goal = both (one codebase → device feel + shareable web); voice mode = deferred/stubbed; backend = minimal real AWS backend.

What the 1-week POC must prove

Grounded in Scribl's own source docs (D2C MLP PRFAQ + MVP Scope + the D2C flow wireframe), not our internal framing. The MVP scope and flow define a tight loop:

  1. Daily prompt — one universal prompt; you only see others' work after you submit yours (submit-to-unlock).
  2. Creative response — a lightweight drawing canvas on the phone (finger-on-glass, color palette, no layers/undo-spirals), plus a short text story; voice is a third mode (deferred for this POC).
  3. Social sharing — up to four private channels (Personal Archive, Family, Friends, Co-Workers) with a standardized set of emoji reactions.
  4. Progression — streaks, stats, badges, milestones; "Your Channel" archive.
  5. Push habit loop — daily reminder, friend activity, momentum re-engagement.

The POC's job is to make the daily loop feel good — especially the drawing — and to be a believable, shareable artifact for "would you do this daily?" feedback. The two make-or-break elements are the finger-on-glass canvas and the push-driven return; both are native-only.

Decision: Expo-OSS-direct vs HTML-first

A Gemini brainstorm and a follow-up AI research report both leaned "Expo directly." We treated those as input to verify, not as the answer. After grounding in Scribl's BRD, the call is clear — but here is the honest comparison.

Recommended

Expo-OSS-direct (one codebase)

  • Validates the native-only risks (canvas feel, push) — the things actually in doubt.
  • Expo Web export = shareable link for desirability, no TestFlight friction.
  • Zero rewrite — the POC is the seed of the production app.
  • Hand-off lands on an RN-oriented team in their real stack.
  • Cost: slightly more setup than a web mock (dev build, Skia); offset by reuse.

Not recommended

HTML / web prototype first

  • Marginally faster to first-clickable with AI web tools (v0/Lovable/Figma Make)…
  • …but can't validate finger-on-glass latency or the push habit loop — the risky parts.
  • Guaranteed web→native rewrite (components, nav, canvas) before team hand-off.
  • Desirability feedback on a desktop/web mock can mislead on a phone-first product.

Risks & honest caveats (recommended path)

  • Expo Web won't exercise push, secure storage, or native voice — those validate on device only. The web link demonstrates flows + drawing; the device build covers the rest.
  • CanvasKit WASM is ~2.9 MB gzipped on web — fine for a demo, noted for later.
  • Voice is stubbed for the week (its scope is still open in the proposal's ADR-0006).
  • One-week scope must be ruthless — see the milestone plan; auth and backend are kept minimal.

No-lock-in architecture: Expo OSS, hosted in AWS

The key distinction the AI reports glossed over: the Expo framework is MIT-licensed open source; "EAS" is Expo's separate paid cloud. We adopt the framework and tooling and avoid the cloud — production runs entirely in AWS.

Layer 1 — adopt OSS / MIT, no lock-in

  • Expo framework + Expo Router; react-native-skia; NativeWind; React Native Reusables; Zustand.
  • Expo's official knowledge skills + Callstack agent-skills; Maestro for E2E.

Layer 2 — avoid EAS cloud → AWS substitute

  • EAS Build → expo prebuild (CNG) + Xcode/Gradle in AWS CodeBuild / GitHub Actions.
  • EAS Update → self-hosted expo-open-ota (S3-backed).
  • EAS Submit/Workflows, the remote Expo MCP, and the EAS-specific Expo skills → not used.

expo prebuild (Continuous Native Generation) generates the real ios/ and android/ projects, which build in our own CI; expo export produces static web assets we host on S3 + CloudFront. This aligns with the proposal's existing AWS CDK decision. Net: all of Expo's OSS value, zero Expo-cloud dependency.

Production architecture (D2C)

The POC runs a thin slice of this — API Gateway + Lambda + DynamoDB, with the Expo Web export on S3/CloudFront. The full planned D2C target is captured (PNG + a diffable Mermaid representation + prose walkthrough) at architecture/README.md.

Request path: end users → Route 53 → AWS WAF → CloudFront (all global) → latency-routed to the nearest active region → Application Load Balancer → Amazon EKS (app services) → Amazon Bedrock → Claude; Amazon Cognito for auth.

Data / state tier

  • Aurora Serverless v2 — relational system of record (ADR-0004).
  • DynamoDB — high-velocity on-demand items.
  • ElastiCache (Redis) + Amazon OpenSearch — always-on cache and search/log baselines.
  • Amazon S3 (media) — cumulative drawing/voice/text store.

Async, observability & analytics

  • Async lane — daily prompt-gen → EventBridge → SQS → EKS; SNS → Pinpoint drives the push habit loop (ADR-0010).
  • Observability — CloudWatch, Amazon Managed Prometheus / Grafana, X-Ray.
  • Analytics & ML — S3 data lake → Glue → Athena + SageMaker, primary region only, gated after Year 1.

Multi-region: launches in us-east-2 (Ohio) (primary; also hosts dev/stage + the data lake), expands prod to eu-west-2 (London) (~month 13) and ap-southeast-1 (Singapore) (~month 25). Each prod region runs its own EKS + Cognito + Aurora + S3 stack. Diagram source of truth: architecture/Scribl_AWS_Architecture_D2C.png.

Transition to the fuller build

Because the POC is built in the production framework, the transition is additive, not a rewrite. The same codebase grows:

  • Auth — swap the stub for Cognito (or chosen IdP).
  • Data — promote the thin backend to the production data model (Aurora Serverless v2 per the proposal's ADR-0004); enforce submit-to-unlock server-side (ADR-0007).
  • AI — add the async pipeline (SQS; ADR-0010) for prompt generation, drawing reflection, and moderation, with Claude model tiering (ADR-0011).
  • Analytics — wire PostHog (ADR-0008).
  • CI/CD — expo prebuild + native build in AWS CodeBuild / GitHub Actions (not EAS Build); OTA via self-hosted expo-open-ota on S3; web build → S3 + CloudFront.
  • Voice — resolve the open scope decision, then add on-device speech where in scope.

CLAUDE.md

# Scribl D2C POC — Claude project guide

## What this is
A ~1-week clickable POC of the Scribl daily-creative-practice app, built in the
**Expo open-source framework** (React Native) as a single codebase that also
exports to web. This POC seeds the production app — it is NOT a throwaway.

## Golden rules
- **OSS only, no Expo-cloud lock-in.** Use the Expo MIT framework + libraries.
  Do NOT use EAS (Build/Update/Submit/Workflows) or the remote Expo MCP.
  Builds, hosting, and CI/CD live in **AWS**.
- **Plan Mode before executing** any multi-file change.
- **Phone-first.** The drawing canvas (finger-on-glass) and the daily loop are
  the point. Validate feel on a device, not just web.

## Stack (locked)
- Expo SDK 56 (OSS) · Expo Router · TypeScript
- @shopify/react-native-skia — drawing canvas (web via CanvasKit + native)
- NativeWind v4 (Tailwind v3) · React Native Reusables (UI) · Zustand (state)
- Backend: thin AWS API Gateway + Lambda (+ DynamoDB) via AWS CDK; mock data
- Voice response: STUBBED for the POC (non-functional button)

## Build / run
- Dev: `npx expo start` (web) · `npx expo run:ios` / `run:android` (device feel)
- Web export (shareable): `npx expo export -p web` → host on S3/CloudFront
- Native: `npx expo prebuild` → build ios/ + android/ in our own CI (no EAS)

## Scope guardrails (1 week)
- Build the loop: prompt → draw/text → submit-to-unlock → channel wall + reactions → streak.
- Auth stubbed unless trivial. Push = device smoke test only.
- Do not add EAS, analytics SDKs, or the production data model yet.

## Data
Mock/seeded JSON via the thin backend: one daily prompt + a few channel responses.

AGENTS.md

# Scribl D2C POC — agent operating notes

This repo is built with AI agents (Claude Code). Read CLAUDE.md first.

## Recommended skills (OSS only)
- Expo official **knowledge** skills (architecture, native UI, tailwind setup,
  expo-module, upgrading). Install: `claude plugin install expo@claude-plugins-official`.
  Do NOT use the EAS deployment / cicd / update-health skills.
- Callstack `agent-skills` (RN performance + best practices).

## Do
- Prefer Expo Router file-based routes and React Native Reusables components.
- Keep the drawing canvas (Skia) responsive — profile on a real device.
- Keep state in Zustand; keep data access behind a thin client over the mock API.

## Don't
- Don't add EAS config, `eas.json`, or the remote Expo MCP.
- Don't depend on `ohah/react-native-mcp` (immature: ~6 stars, stale).
- Don't introduce a web→native split — one codebase, web is an export target.

## Verify before "done"
- App runs on web AND at least one device/simulator.
- Drawing feels smooth on-device; submit-to-unlock actually gates the feed.
